# Зоны повышенного спроса и «ценность пункта назначения»

Модуль `feature-demand-zones` (Android) + расширение сервиса `demand` (backend). Общая архитектура —
[architecture.md](architecture.md); скоринг — там же, раздел 4; события — раздел 5.2.

Две задачи:

1. **Получить** карту повышенных коэффициентов (красные/оранжевые зоны), которую Bolt и Uber рисуют
   на карте водителя, — API для этого нет.
2. **Использовать** её и другие сигналы спроса (закончившийся концерт/матч, посадки самолётов за последние
   15–20 минут, швартовка судна) так, чтобы невыгодный сам по себе заказ **в горячее место** оценивался
   с учётом того, что он привезёт водителя туда, где с высокой вероятностью будет хороший следующий заказ.

## 1. Как Bolt и Uber показывают спрос

| Платформа | Что на карте | Где ещё виден спрос |
|-----------|--------------|---------------------|
| Uber Driver | Шестиугольные ячейки (H3) с заливкой от жёлтого к тёмно-красному; внутри часто **число** — множитель («1.4x») или доплата («+6 zł»); легенда внизу | на карточке заказа — строка сурж-доплаты; push «Wysoki popyt w okolicy»; в «Odkrywaj» — Boost+-зоны (это акция, а не сурж — см. promotions.md) |
| Bolt Driver | Плавные «тепловые пятна» (градиент оранжевый → красный) без ячеек; в части рынков — подпись «Zwiększony popyt +20 %» при касании | на карточке — тег повышенного тарифа / цена уже с множителем; push «Duże zapotrzebowanie w Śródmieście» |

Общее: карта спроса показывается на **главном экране ожидания** обоих приложений — именно там
водитель проводит время между заказами. Это и есть окно для чтения.

## 2. Пять источников данных о спросе (от пассивных к активным)

### 2.1 Вывод суржа из самих карточек (пассивно, бесплатно, всегда)

Каждое предложение — измерение цены в точке подачи. Тарифная модель региона (`TariffLearner`,
architecture.md 4.6) предсказывает «обычную» цену по км и минутам; **остаток** и есть множитель:

```
surge_obs = price_card / tariff_model(trip_km, trip_min, platform)      // 1.0 = нет суржа
→ наблюдение (platform, pickup_h3, t, surge_obs, confidence)
```

Uber иногда пишет сурж явно («+6,10 zł за повышенный спрос») — тогда наблюдение точное. Десятки
водителей региона дают сотни таких точек в час; сервер собирает их в поле суржа (раздел 3). Этот
источник не требует ни скриншотов, ни разрешений и работает с первого дня — но покрывает только
места, откуда приходят предложения.

### 2.2 Уведомления платформ

`NotificationListenerService` уже есть: «Wysoki popyt: Wrzeszcz 1.6x», «Duże zapotrzebowanie w
okolicy lotniska». Парсер: название района/объекта → геокод из справочника региона (OSM
`place=suburb/neighbourhood`, аэропорт, вокзал) → наблюдение по гексам района с `confidence` 0.5.

### 2.3 Чтение карты с экрана (основной источник полной картины)

Карта рендерится в `MapView`/Canvas — `AccessibilityService` её не видит. Единственный путь —
**снимок экрана** (`MediaProjection`) и анализ пикселей.

**Когда снимать.** Только когда (а) в foreground главный экран ожидания Bolt или Uber (определяется
по `AccessibilityEvent` окна и отсутствию карточки заказа), (б) прошло ≥ `demand_capture_interval`
(по умолчанию 90 с) с прошлого снимка или водитель сместился > 500 м, (в) экран включён. В пути с
пассажиром карта не снимается. Типичная смена — 100–200 снимков.

**Разрешение.** `MediaProjection` требует согласия пользователя; на Android 14+ — при каждом запуске
захвата (сессия живёт, пока жив foreground-сервис с типом `mediaProjection`). Запрашиваем при старте
смены одним диалогом: «Разрешить TaxiPilot читать карту спроса Bolt/Uber в течение смены». Снимок
не сохраняется и никуда не уходит — только извлечённые полигоны/ячейки.

**Анализ (на телефоне, ≤ 150 мс на снимок, даунскейл ×4):**

1. Маска цветовых классов в HSV: для Uber — дискретные ступени жёлтый/оранжевый/красный/бордовый
   (калибруются по легенде внизу экрана: легенда даёт соответствие цвет → множитель); для Bolt —
   непрерывная интенсивность красного канала поверх базовой карты (фон вычитается по эталонному
   снимку карты без спроса).
2. Сегментация: Uber — шестиугольники (поиск контуров, фильтр по площади и форме; центр каждой ячейки);
   Bolt — связные области с уровнями 0.3/0.6/0.9 от максимума.
3. OCR (ML Kit, on-device) по центрам ячеек Uber — множитель или сумма; по легенде — шкала.
4. Привязка пикселей к координатам (ниже).
5. Результат: список `(h3_cell, surge_mult_est, source=SCREEN, confidence, t)`.

**Привязка пиксель → координаты.** Нужны центр, масштаб и ориентация карты. Способы, по убыванию
надёжности, применяются каскадом:

| Способ | Как | Точность |
|--------|-----|----------|
| **A. Подписи карты** | ML Kit читает названия улиц/районов/объектов с их пиксельными координатами; названия ищутся в офлайн-справочнике топонимов региона (OSM, с сервера); по ≥ 3 совпадениям решается преобразование подобия (масштаб, сдвиг, поворот). Повторяющиеся названия отсекаются через RANSAC | 1 ячейка H3 res 9 (~170 м) |
| **B. Маркер машины + масштаб** | Маркер водителя = его GPS; масштаб запоминается с последней успешной калибровки A (водители редко меняют зум) или из настройки «масштаб по умолчанию»; ориентация — север вверх (режим по умолчанию в обоих приложениях в ожидании) | 1–2 ячейки |
| **C. Калибровка движением** | Пока машина едет, подписи на карте смещаются на Δpx при смещении GPS на Δm → метры на пиксель | масштаб ±5 % |
| **D. Ручная** | Один раз: «не трогая зум, коснитесь на карте Bolt двух известных мест» (приложение накладывает прозрачную сетку поверх) | по желанию |

Если калибровка не удалась (`confidence` < 0.5) — снимок отбрасывается, данные берутся из 2.1/2.4.

**Ограничения, которые надо проверить на первом прототипе:** тёмная тема карты, пользовательский
зум, 3D-наклон (в ожидании обычно отсутствует), перекрытие карты плашками приложения (нижняя
треть экрана исключается из анализа).

### 2.4 Сообщество (сервер)

Сурж — свойство места, а не водителя: ячейка, прочитанная одним водителем региона, актуальна для
всех. Сервер объединяет наблюдения 2.1–2.3 от всех водителей в **поле спроса региона** (раздел 3) и
раздаёт его пакетом каждые 60 с (WebSocket/poll) всем, кто онлайн в регионе. Один водитель со
включённым чтением экрана «освещает» район для десятка без него. Также — честная оценка `confidence`
по числу независимых наблюдений и их свежести.

### 2.5 Собственная история

Тепловая карта по гексам × час недели из истории предложений и суржей (architecture.md 5.1,
`demand`) — базовый уровень, когда свежих наблюдений нет: «в пятницу в 23:00 на Długi Targ сурж
бывает в 70 % случаев».

## 3. Поле спроса (`DemandField`)

Единое представление для скоринга, на телефоне (кеш) и сервере:

```
DemandCell {
  h3 (res 9), platform (BOLT | UBER | ANY),
  surge_mult: Double,          // лучшая текущая оценка множителя, 1.0 = норма
  surge_observed_at: Instant,  // последнее наблюдение
  surge_confidence: Double,
  base_demand: Double,         // исторический спрос, предложений/час на ячейку в этот час недели
  event_outflow: Double,       // ожидаемый поток людей/15 мин от событий рядом (раздел 4.2)
  airport_wave: Double,        // ожидаемые пассажиры на выходе/15 мин (раздел 4.3)
  ship_wave: Double,
  updated_at: Instant
}
```

**Затухание суржа.** Красная зона живёт 10–40 минут. Оценка множителя на момент прибытия водителя:

```
surge_mult(t) = 1 + (surge_observed − 1) × exp(−(t − observed_at) / τ_surge)
```

`τ_surge` — по умолчанию 20 мин, обучается на сервере по парам наблюдений одной ячейки (сколько
реально держится сурж в этом регионе/даypart). Если прибытие через 25 минут, а сурж виден сейчас —
учитываем лишь ~30 % его величины. Это главное, что отличает честную оценку от «красная — едем».

## 4. Сигналы спроса в пункте назначения

### 4.1 Сурж

`surge_mult(dropoff_h3, t_arrival)` из поля с затуханием; соседние ячейки (кольцо 1) с весом 0.5 —
сурж-зона шире одной ячейки, а подача придёт и из соседней.

### 4.2 События: концерт, матч закончился

Из `events` (architecture.md 5.2): для площадок в радиусе `event_radius` (по умолчанию 1,5 км) от
высадки — ожидаемый отток людей на момент прибытия:

```
outflow(t) = expected_people × curve(t − ends_at)
curve: 0 до окончания; пик 10–25 мин после; хвост до 60 мин (спорт — быстрее, концерт — дольше)
```

Окончание берётся по расписанию и уточняется: по факту (сурж вспыхнул у площадки — событие
закончилось; водители рядом принимают заказы от площадки), по ручной отметке «закончилось». Если
`ends_at` неизвестно (концерт без длительности) — типовая длительность по типу площадки.

### 4.3 Аэропорт: посадки за последние 15–20 минут

Из OpenSky/ADS-B (`FLIGHT` события): самолёт сел в `t_land` → пассажиры на выходе через 25–40 мин
(багаж, паспортный контроль для non-Schengen дольше: +15 мин). Если заказ везёт водителя к аэропорту
с прибытием через 20 минут, релевантны посадки в окне `[t_arrival − 40, t_arrival − 20]` — то есть
**как раз те, что сели за последние 15–20 минут и садятся сейчас**:

```
airport_wave(t_arrival) = Σ по посадкам: seats(aircraft_type) × load_factor × share_taxi × window(t_arrival − t_land)
```

Для аэропортов с **виртуальной очередью** Bolt/Uber (большинство крупных): волна важна тем, что
очередь быстро рассасывается; ожидаемое время в очереди оценивается по волне и типичному числу
машин (обучается по фактам: приехал в аэропорт → через сколько пришёл заказ). Аналогично для
паромных терминалов (`ship_wave`) и вокзалов (поезда дальнего следования).

### 4.4 Историческая база и «мёртвые» зоны

`base_demand` для ячейки в этот час недели. Низкая база (пригород ночью) — отрицательный сигнал:
даже без явного «штрафа» ожидаемая ценность следующего заказа там мала.

## 5. Ценность пункта назначения в скоринге

Вместо качественных множителей `zone_factor` и `event_factor` (architecture.md 4.3) вводится
**количественная добавка к `net`**, как у бонусов акций: ожидаемый выигрыш от того, что следующий
заказ будет искаться из точки высадки, а не из текущей.

```
EV_next(cell, t) = P_order(cell, t) × E_net(cell, t)

P_order(cell, t)  = вероятность получить заказ в течение horizon (по умолчанию 15 мин)
                  = 1 − exp(−λ(cell, t) × horizon)
λ(cell, t)        = base_demand × surge_boost(surge_mult) + k_event × outflow + k_air × airport_wave + k_ship × ship_wave
E_net(cell, t)    = median_net(region, daypart) × surge_mult(t)      // при сурже заказы дороже

dest_value   = EV_next(dropoff_h3, t_arrival) − EV_next(origin_h3, now)
dest_bonus   = clamp(dest_value × dest_weight, −dest_cap, +dest_cap)   // по умолчанию weight 1.0, cap 25 zł

net_eff      = net + marginal_bonus (акции) + dest_bonus
```

Далее — обычные `R_km`, `R_h`, `E` на `net_eff`. Что это даёт:

- **Невыгодный заказ в красную зону.** Uber 9,54 zł (нетто 6,6, `E` 0,56 → пропустить) с высадкой в
  ячейке с суржем ×1,6, наблюдённым 5 мин назад (на момент прибытия через 11 мин ≈ ×1,45), база
  4 предложения/ч → `P_order` за 15 мин ≈ 0,8; `E_net` ≈ 18 × 1,45 ≈ 26 → `EV_next` ≈ 21; из текущей
  точки (база 1,5/ч, без суржа) `EV_next` ≈ 0,31 × 18 ≈ 5,6 → `dest_bonus` ≈ +15 zł → `net_eff` 21,6,
  `E` ≈ 1,3 → **брать**. Озвучка: «Uber, 9 злотых — слабый, но высадка в красной зоне, ×1,5. Брать.»
- **Хороший заказ в мёртвую зону.** `dest_bonus` отрицательный (до −cap) — честно показывает цену
  пустого возврата, согласованно с `return_weight` для длинных поездок (для длинных `dest_value`
  считается, но `return_km` уже учтён — чтобы не удваивать, `dest_bonus` там ограничен +cap/2).
- **Аэропорт с волной.** Заказ 18 zł в аэропорт за 22 минуты; за последние 15 минут сели три борта
  (A320 ×2, 737) → на выходе через 25–40 мин ≈ 450 пассажиров, `share_taxi` 0,12 → ~55 заказов за
  волну, очередь рассосётся за ~10 мин → `P_order` ≈ 0,9, `E_net` аэропортовый (медиана заказов из
  аэропорта, обычно ×1,5 от городской) → `dest_bonus` ≈ +20 zł.
- **Матч закончился 10 минут назад**, заказ везёт к стадиону с прибытием через 12 минут — попадаем в
  пик оттока (20–25 мин после финала) → большой `outflow`, высокий `dest_bonus`. Если прибытие через
  45 минут — хвост, `dest_bonus` мал. Модель сама различает «успеваем» и «опоздали».

Калибровка: по каждому принятому заказу логируются `dest_bonus_applied` и факт — через сколько минут
после высадки пришёл следующий заказ и каков был его `net`. Сервер подбирает `k_event`, `k_air`,
`τ_surge`, `share_taxi`, `horizon` так, чтобы предсказанный `EV_next` совпадал с фактическим.

Оверлей показывает причину добавки одной строкой: «→ Oliwa ×1,5 (6 мин назад)», «→ Lotnisko: 3 посадки,
волна через 15 мин», «→ Ergo Arena: концерт закончился 12 мин назад». На дисплее магнитолы — вторая
строка карточки.

## 6. Зоны для позиционирования (без заказа)

Та же `EV_next` по всем ячейкам в радиусе 6 км — это и есть рекомендация «куда ехать» (architecture.md
5.3), теперь с живым суржем: `value(cell) = EV_next(cell, t_arrive) − travel_cost(here → cell)`,
с гистерезисом, чтобы не гонять водителя за каждой вспышкой. Красная зона в 2 км с суржем ×1,8,
наблюдённым минуту назад, и ожидаемым затуханием за 8 минут пути → ехать; та же зона в 6 км — нет.

## 8. Данные

- `surge_observations` — platform, h3, t, surge_mult, source (CARD / NOTIF / SCREEN / COMMUNITY), confidence, driver_id (null в общем поле).
- `demand_field` — текущее поле региона (материализованное представление, обновляется каждые 60 с).
- `demand_calibration` — `τ_surge`, `k_event`, `k_air`, `share_taxi`, `horizon` по региону.
- В `decisions`: `dest_bonus_applied`, `dest_reason`, `surge_at_dropoff_est`; в `outcomes`: `next_order_after_min`, `next_order_net`.

## 9. Отчёты ([reports.md](reports.md))

По часам: `dest_bonus_decisions` (решения, изменённые ценностью назначения), `surge_cells_seen`,
`median_surge_at_pickup`. За сутки: «точность прогноза назначения» — предсказанный `EV_next` vs факт
(минуты до следующего заказа и его `net`) для заказов с `dest_bonus` > 0 и без; `surge_capture_coverage`
(доля смены, когда поле спроса было свежим). Инсайт: «4 заказа приняты ради горячей зоны: средний
следующий заказ пришёл через 4 мин с нетто 27 zł против 11 мин и 17 zł в обычных случаях».

## 10. Риски и проверки

| Риск | Смягчение |
|------|-----------|
| Привязка снимка к координатам ненадёжна | Каскад A→D, отбрасывание при низкой уверенности, калибровка по сообществу (совпадение ячеек разных водителей) |
| `MediaProjection` на Android 14+ требует согласия каждый раз | Один запрос на смену, foreground-тип `mediaProjection`; источники 2.1/2.2/2.4 работают и без него |
| Батарея и нагрев | Снимок раз в 90 с, даунскейл, анализ ≤ 150 мс; отключение при < 15 % заряда |
| Переоценка суржа («едем в красное, а оно погасло») | Затухание с обучаемым τ, потолок добавки, калибровка по фактам |
| Платформы меняют палитру/легенду | Калибровка по легенде на каждом снимке; словарь палитр с сервера |
