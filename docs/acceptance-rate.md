# Контроль показателя принятия заказов

Модуль `feature-acceptance` (Android). Общая архитектура — [architecture.md](architecture.md);
политика решения — [order-capture-and-parsing.md](order-capture-and-parsing.md), раздел 4; акции с
условиями по принятию — [promotions.md](promotions.md).

## 1. Зачем

Показатель принятия (Uber «Wskaźnik akceptacji», Bolt «Wskaźnik akceptacji») влияет на доступ к
акциям (Quest требует ≥ 25 %), на статусы (Uber Pro), на приоритет и видимость заказов у Bolt и — по
опыту водителей — на качество выдачи при падении к 50 % и ниже. Приложение, которое советует
пропускать невыгодные заказы, обязано одновременно беречь этот показатель. Три задачи:

1. **Знать** текущий показатель на каждой платформе и как он изменится от следующего решения.
2. **Не тратить** показатель там, где его можно не тратить: заказы, пришедшие **во время текущей
   поездки**, не отклонять, а **тихо игнорировать** — истечение таймера в этом состоянии платформы
   не засчитывают как отказ.
3. **Предупреждать**, когда показатель снижается к 50 %, и менять поведение советника, пока он не
   восстановится.

## 2. Три исхода вместо двух

К `Accepted` / `Declined` добавляется третий исход решения — `Ignored`:

| Исход | Что делает приложение | Что делает платформа |
|-------|-----------------------|----------------------|
| `ACCEPTED` | подсвечивает «Принять» / автотап | заказ назначен, считается принятым |
| `DECLINED` | явное отклонение: тап по «Отклонить»/«X» (или водитель сам) | засчитывается как отказ (кроме Bolt-предложений с тегом `NO_PENALTY_DECLINE`) |
| `IGNORED` | **ничего не нажимает**, скрывает оверлей, не озвучивает призыв к действию; карточка истекает сама | зависит от состояния: во время активной поездки — не засчитывается как отказ (по умолчанию); в свободном состоянии — истечение таймера обычно засчитывается как пропуск наравне с отказом |

### 2.1 Таблица «что засчитывается» (`AcceptancePolicyTable`)

Правила по платформе и состоянию водителя — конфиг с сервера, переопределяемый водителем, потому
что платформы меняют правила и они различаются по странам:

| Платформа | Состояние | Явный отказ | Истечение (игнор) | Отказ с тегом «не повлияет» |
|-----------|-----------|-------------|-------------------|-----------------------------|
| Uber | свободен | считается | считается (как «пропущено») | — |
| Uber | **в поездке** (следующий заказ) | считается | **не считается** | — |
| Bolt | свободен | считается | считается | не считается |
| Bolt | **в поездке** (следующий заказ) | считается | **не считается** | не считается |

Таблица **проверяется автоматически**: приложение сравнивает свой счётчик с показателем, который
читает с экранов платформ (раздел 3.2). Если после серии «игноров в поездке» показатель платформы
упал — правило для этой ячейки помечается «считается», водитель получает уведомление, политика
переключается. Так ошибка в предположении обнаруживается за один-два дня, а не копится.

### 2.2 Поведение в поездке

Состояние «в поездке» определяется по окну Bolt/Uber (экран навигации к пассажиру / поездка;
якоря «Rozpocznij przejazd», «Zakończ», имя пассажира в шапке) и подтверждается GPS-движением после
принятия. Когда в этом состоянии приходит карточка следующего заказа:

- скоринг работает как обычно (заказ может быть хорошим — тогда «Принять»);
- если вердикт «Пропустить» или «На усмотрение» без подтверждения водителя — исход **`IGNORED`**:
  оверлей показывает серую плашку «Пропускаем тихо — не отклоняйте», TTS короткая («Следующий —
  слабый, игнорирую»), **никаких тапов**; таймер карточки истекает сам;
- кнопка руля `PREVIOUS` в поездке означает «игнорировать», а не «отклонить»: автотап отклонения в
  поездке **запрещён** политикой независимо от настроек;
- если водитель всё же нажимает «Отклонить» сам — исход `DECLINED`, приложение один раз напоминает:
  «В поездке лучше не отклонять, а дать истечь — отказ не засчитается»;
- `feature-autotap` в режиме автоприёма в поездке принимает только заказы, прошедшие условия
  политики; остальные игнорирует.

Важно для Uber: предложения из списка «Zlecenia w pobliżu / Trip Radar» (водитель сам выбирает) на
показатель не влияют — они помечаются отдельно и в знаменатель не идут.

### 2.3 Поведение в свободном состоянии

Истечение здесь обычно считается наравне с отказом, поэтому «тихо игнорировать» бессмысленно — но
важно **не тратить отказ дважды**: если решено пропустить, приложение рекомендует явное
отклонение сразу (быстрее освобождает слот и у Uber не копит «пропущено»), а для Bolt-предложений с
`NO_PENALTY_DECLINE` отмечает «бесплатный отказ».

## 3. Измерение показателя

### 3.1 Собственный счётчик

```
acceptance(platform) = accepted / (accepted + counted_declines + counted_expirations)
```

по скользящему окну `acceptance_window` (настройка; по умолчанию последние **50 предложений** на
платформу — окно подбирается автоматически так, чтобы наш счётчик совпадал со значением платформы,
см. 3.2). Знаменатель наполняется по таблице 2.1 — предложения, которые по таблице «не считаются»,
в него не входят.

Отдельно ведётся **прогноз**: «если следующие N решений — отказы, показатель будет X %».

### 3.2 Значение платформы с экрана

Тот же `AccessibilityService` читает показатель там, где платформа его показывает: Uber —
профиль/Uber Pro, условия Quest («Wskaźnik akceptacji: 25 %» — это требование, не значение;
фактическое — на экране статуса), Bolt — «Statystyki / Wyniki» («Wskaźnik akceptacji 78 %»).
Экстрактор: `(akceptacji|принятия|acceptance)\D{0,30}(\d{1,3})\s*%` с контекстом «ваш/twój».
Каждое прочитанное значение — опорная точка: счётчик калибруется (окно, таблица «что считается»).
Напоминание открыть экран статистики — раз в смену, вместе с напоминанием про акции.

### 3.3 Доверие

Оверлей показывает показатель с пометкой источника: «78 % (Bolt, 2 ч назад)» или «≈ 74 % (расчёт)».
Расхождение между расчётом и значением платформы > 5 п.п. — сигнал проверить таблицу 2.1.

## 4. Алерты

Пороги настраиваются; по умолчанию относительно 50 %:

| Уровень | Условие (по платформе) | Реакция |
|---------|------------------------|---------|
| Внимание | показатель ≤ 60 % **или** прогноз «ещё 3 отказа → ≤ 55 %» | жёлтая плашка в оверлее и на дисплее магнитолы «Принятие Bolt 59 %», TTS один раз: «Принятие Болт пятьдесят девять процентов» |
| Предупреждение | ≤ 55 % | оранжевая плашка; советник переходит в режим **«берегу показатель»** (раздел 5); push, если приложение свёрнуто |
| Критично | ≤ 50 % | красная плашка, TTS при каждом «Пропустить»: «Внимание, принятие пятьдесят процентов»; в автоприёме порог `minScoreRatio` снижается до 1.0; ежечасное напоминание, пока не поднимется выше 55 % |
| Акция под угрозой | до порога активной акции < `acceptance_safety_margin_pp` (5 п.п.) | как «предупреждение» + текст «Отказ сорвёт бонус 110 zł» (promotions.md 4.2) |

Алерт по каждой платформе отдельно; снимается с гистерезисом (+3 п.п. выше порога), чтобы не
дёргать. Все алерты пишутся в журнал и видны в отчёте дня.

## 5. Режим «берегу показатель»

Включается автоматически при уровне «предупреждение» (или вручную тумблером), выключается при
восстановлении выше порога + гистерезис:

| Что меняется | Как |
|--------------|-----|
| Порог потока `E*` | понижается плавно: `E* × (1 − k × дефицит_пп / 10)`, `k` = 0.15 — на 10 п.п. ниже цели порог мягче на 15 % |
| «На усмотрение» | трактуется как «Брать», если отказ стоит показателя |
| Цена отказа | к `E` отклоняемого добавляется `acceptance_cost` — оценка потерь от падения показателя (настройка `acceptance_point_value`, по умолчанию 3 zł за п.п. ниже 60 %; ниже 50 % — 8 zł) |
| В поездке | всё невыгодное — только `IGNORED` (и так по умолчанию) |
| Бесплатные отказы | предпочтение Bolt-предложениям с `NO_PENALTY_DECLINE` для «тренировки» отказов не нужно, но они остаются бесплатными |
| Озвучка | в вердикт добавляется «принятие 54 %» |
| План восстановления | плашка «До 60 %: принять 4 из следующих 5» — считается по окну |

Режим не заставляет брать убыточное: жёсткое правило себестоимости остаётся. Если даже с учётом
`acceptance_cost` заказ невыгоден — «Пропустить», но советник предлагает способы отказа без потери
(дать истечь в поездке, бесплатный отказ Bolt) и показывает, сколько ещё отказов можно себе позволить.

## 6. Взаимодействие с другими модулями

- **Promotions:** `decline_cost` акции и `acceptance_cost` показателя складываются; показатель в окне
  акции считается по правилам акции (Bolt «kwalifikujących się»).
- **Автоприём:** политика получает `acceptance_state`; в поездке запрещает отклонение; при «критично»
  может быть включён авто-режим «принимать всё выше себестоимости до восстановления» (опция
  `auto_recover_acceptance`, выкл по умолчанию).
- **Кнопки руля:** `PREVIOUS` = «отклонить» в свободном состоянии, «игнорировать» в поездке; дисплей
  магнитолы показывает показатель второй строкой при уровне «внимание» и выше.
- **Отчёты:** см. раздел 8.

## 7. Настройки (экран «Показатель принятия», в каталог architecture.md 4.7)

| Параметр | Ключ | По умолчанию |

| Гистерезис | `acceptance_hysteresis_pp` | 3 п.п. |

| Напоминать открыть статистику платформы | `acceptance_screen_reminder` | раз в смену |

## 8. Данные и отчёты

- `decisions.outcome` получает значение `IGNORED`; поля `on_trip` (bool), `counts_toward_acceptance`
  (bool, по таблице), `acceptance_before`, `acceptance_after_est`.
- `acceptance_readings` — значения с экранов платформ: platform, value_pct, read_at, screen.
- `acceptance_alerts` — уровень, платформа, время, значение, что сделал водитель после.

В [reports.md](reports.md): по часам — `acceptance_bolt`, `acceptance_uber` (расчёт и последнее
значение платформы), `ignored_on_trip`, `declines_counted`, `free_declines`; за сутки — траектория
показателя по платформам, `ignored_saved_pp` («тихие игноры сохранили ≈ 6 п.п.»), алерты и реакция,
`policy_table_mismatches`. Инсайт: «Bolt: принятие 71 % → 64 % за смену; 5 отказов в свободном
состоянии; 7 слабых заказов в поездке проигнорированы без потерь».

## 9. Тестирование

- Юнит: счётчик по окну с таблицей «что считается», прогноз, гистерезис алертов, `acceptance_cost`.
- Сценарий «в поездке пришёл слабый заказ»: оверлей без кнопки отклонения, руль `PREVIOUS` → `IGNORED`,
  автотап не вызывается, карточка истекает → исход и счётчик корректны.
- Автопроверка таблицы: синтетическая серия игноров + «прочитанное» падение показателя → переключение
  правила и уведомление.
- Полевой: неделя наблюдений на обеих платформах — сверка счётчика со значениями на экранах, фиксация
  реальных правил зачёта для Польши.
